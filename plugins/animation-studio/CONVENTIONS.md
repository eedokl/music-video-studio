# animation-studio – conventions for every skill in this plugin

Read this before adding or changing a skill. It keeps the plugin free of duplicates and portable.

## Layout

```
animation-studio/
  .claude-plugin/plugin.json
  README.md            what the plugin does, the skills, how to install
  TOOLS.md             external programs and AI models: used / recommended / optional
  CONVENTIONS.md       this file
  skills/<skill>/SKILL.md, scripts/, references/, assets/      (user skills)
  skills/<block>/BLOCK.md, scripts/, references/, assets/      (building blocks - not skills)
  tests/smoke.py       static checks;  tests/e2e/run.py  end-to-end builds per film type
```

Two kinds of folders under skills/:
- **User skills** (one per kind of video the user asks for): thin. Interview → creative brief → build →
  review checkpoints. Their SKILL.md is what the user sees; frontmatter `name` + a "pushy" `description`.
- **Building blocks** (studio-core, song-analysis, toon-2d, film-finish, characters, voice, ai-video, bricks-3d):
  scripts + knowledge used by several user skills, written once. Their doc is `BLOCK.md` (no frontmatter), NOT a
  SKILL.md: Claude Code loads the description of every skill into every session, so blocks stay out of that list
  and cost no context until a user skill sends Claude to read them. Every user SKILL.md carries the standard
  "Building blocks" paragraph with `${CLAUDE_PLUGIN_ROOT}/skills/<block>/BLOCK.md`; inside BLOCK.md (and references)
  write `<plugin>` for the plugin folder - `${CLAUDE_PLUGIN_ROOT}` is substituted only in SKILL.md. A new block gets a
  BLOCK.md and is added to that paragraph in every user skill; a new user skill copies the paragraph.
Anything two user skills need goes into a building block – never copy code between skills.

## Language and paths

- English everywhere: SKILL.md, references, script names, code, comments, CLI help, printed messages, JSON keys.
  Examples (lyrics, gag texts, German songs) may stay German.
- No absolute paths and nothing outside the plugin in any file. Scripts find sibling skills with the per-skill
  helper `scripts/_studio.py`:  `import _studio; _studio.use("song-analysis", "toon-2d")` (studio-core is always
  added) and `_studio.skill_dir("toon-2d")` for assets. `_studio.py` is identical in every skill (edit
  studio-core's copy, copy it to all skills); it keeps the skill's own `scripts/` first on `sys.path`. Do not add a
  module whose name already exists in another skill (`tests/smoke.py` fails on new duplicates).
- External programs and machine paths only through `studio-core/scripts/config.py`: `config.need("synfig")`,
  `config.get("earshot")`. They come from environment variables or the machine config
  `~/.animation-studio/config.json` written by `check_tools.py --setup` / `--set key=value`.
- In SKILL.md, call scripts as `uv run "${CLAUDE_PLUGIN_ROOT}/skills/<skill>/scripts/x.py"` (substituted by Claude
  Code when the skill loads - ONLY in SKILL.md; in references/ and other files write
  "`skills/<skill>/scripts/x.py` of this plugin" or refer to the SKILL.md command). Always quote the path.
  Run them with `uv run "${CLAUDE_PLUGIN_ROOT}/skills/<skill>/scripts/x.py" ...` - never with hand-written `--with` lists.
- Every script that is run with uv starts with PEP 723 inline metadata listing exactly the third-party packages it
  imports, including those of the plugin modules it imports through `_studio.use(...)`, with exact pins
  (`# /// script` / `# requires-python = ">=3.12"` / `# dependencies = ["numpy==2.5.4", ...]` / `# ///`);
  plus `# [tool.uv]` / `# exclude-newer = "<date>"` - ONE date for all scripts, so the packages the pinned ones pull
  in are fixed too (move every pin and the date together when re-pinning; smoke.py checks it);
  stdlib-only CLIs declare `dependencies = []`. Modules that are only imported need no header. Scripts run by
  another interpreter (Blender targets, `gpu_python` / `tts_python` workers, Krita) get no header but a one-line
  comment naming that interpreter. A script that starts another plugin script whose packages it does not declare
  itself runs it with `config.script_cmd(path)` (= `uv run path`). `tests/smoke.py` checks the headers.
- Before a release: `python tests/smoke.py` and `python tests/e2e/run.py --full` (end-to-end builds of every film type from
  synthetic input; all PASS, SKIP only for programs the machine lacks - see README "Checking the plugin"), then bump
  `version` in `.claude-plugin/plugin.json`. A change to a build path gets an e2e test (tests/e2e/test_<film type>.py,
  synthetic input generated by the test, no binary fixtures, no downloads, no GPU AI jobs).

## Shared machinery

- GPU: any AI model run takes the shared lock first: `from gpu_lock import acquire; acquire("job", model="...")`.
  It waits for other jobs and flushes ComfyUI on a model change. Never delete another job's lock.
- Song projects: `song-analysis/scripts/song_project.py` (`Project`): `project.json`, `song.wav`, `lyrics.txt`,
  `stems/`, `analysis/`, `cache/`. Times are always song seconds.
- Picture: each section renders to `scenes/<section>/f.%04d.png` (any renderer); `film-finish/scripts/build.py`
  assembles preview and film (film.mp4, film_small.mp4 < 30 MB, film_mail.mp4 ~12 MB), applies the look once and
  checks every file (0 decode errors).
- Caches and derived artefacts (stills rendered from a rig, normalized SVGs, spoken lines, sound-bank renders, composites over raw frames): `studio-core/scripts/derived.py`, never an ad-hoc stamp. `derived.fresh(target, inputs, spec)` / `with derived.build(target, inputs, spec) as b:` - freshness is a content hash of the input files plus a JSON spec of every setting that changes the result (text, size, scale, voice, engine, version when one is cheaply known), never mtimes (copy / zip / git checkout must not trigger or skip a rebuild); the record holds no absolute paths and is written only after the build succeeded (temp + rename), so an interrupted build never looks fresh. A pass that writes into a folder another program also writes uses `derived.Ledger` to recognise its own files. When replacing an older cache format, adopt or migrate its files (an existing project must not lose work or re-run an expensive step needlessly).
- Media helpers: `studio-core/scripts/media.py` (decode, duration, voice activity, check_video, contact_sheet).
- Project check: every entry script of a user skill (and every film-finish script that reads project.json) validates
  the project file FIRST, before any long step: `P.check("<skill>")` on a `Project`, or
  `project_check.require(path_or_dict, skill="<skill>")` (studio-core `project_check.py`; also a CLI). Errors (wrong
  type of a shared key, overlapping / unordered / duplicate sections, a talking figure's voice not in the cast, a
  speaking slide figure without a mouth block, an unknown transition kind ...) stop with exit code 2 and a message naming
  the key and what is expected; warnings (unknown keys with did-you-mean, stale rendered frames) are printed. The
  schema is plain Python data (`SCHEMAS` in `project_check.py`, one dict per project family: song, talk, short, deck):
  **a new project.json key must be added there** (with its type), otherwise every build warns about it.
- Frame size: project.json `"size": [w, h]` (default 1280x720). Read it with `P.size` (song_project) or
  `project_check.frame_size(p)` - never hard-code 1280x720 in a film path; pixel values designed at 720p (fonts, title
  y, card places) are multiplied by `P.scale` (= h / 720). Default output must stay identical without "size".

## Creative seed (keep films fresh)

Every project has `"seed"` and `"ideas"` (see `studio-core/scripts/creative.py`).
- Variation comes from `creative.rng(P, salt)` / `creative.pick(...)` – same seed, same film; new seed, new take.
- Every user skill has a **creative brief** step: before building, invent ideas that come from *this* song or
  topic (a concrete image per lyric idea, props, gags, an ending) and record them with `creative.add_idea`. User
  ideas are recorded with `by: "user"` and always win. Reference projects show techniques, never a template to copy.
- Defaults are a starting point, not the film: a skill that produces the same routine for every song is broken.

## Tests

- Each user skill has `references/reference-tests.md`: which earlier project is its reference, how to rebuild a
  part of it with the skill, what was compared (measurements + contact sheets) and the result.
- Run tests in a scratch folder outside the plugin; never modify the reference projects.
